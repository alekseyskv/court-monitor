# Наборы судов в Legalic: что нужно от клиента court-monitor и справочника судов

Дата: 10.10.2026
Кому: Алексею (пакет lawmatic/court-monitor, справочник courts.lawmatic.ru)
От: Сергей (разбор и реализация в Legalic)

Legalic научился искать дела и вести мониторинг сразу по **набору судов**:
суды, порталы «все сразу» (mos-gorsud, mos-sud, КАД, ВС РФ) и выборки по
справочнику (регион × тип суда, подчинённые суды). Ниже — что из этого касается
пакета и справочника. Про сами парсеры и оркестратор — соседний документ
`court-parsers/docs/legalic-court-sets-requests.md`.

Полный разбор и решения — `legalic-frontend/docs/court-set-selection-plan.md`.

---

## 1. Клиент: метод для задания по многим судам

Когда в prsr появится задание поиска по многим судам (court-parsers, п. 1 —
`targets[]`, очередь `bulk`, прогресс и результаты по целям), в пакете нужен
метод под него, например:

```php
$job = $client->createMultiSearchJob(
    targets: [
        ['parser_id' => 'moscow', 'court_id' => '', 'process_types' => ['2', '4', '5']],
        ['parser_id' => 'federal', 'court_id' => 'kovrovsky--wld', 'process_types' => ['civil', 'civil_appeal']],
    ],
    params: ['members' => 'Жилищник', 'date_from' => '01.01.2026'],
    options: ['queue' => 'bulk', 'max_cases' => 20000, 'max_captcha' => 12000],
);
```

и чтобы `getJob()` / `getJobResults()` отдавали прогресс и строки **с целью**.
Сейчас Legalic ставит `createSearchJob()` на каждый сайт
(`legalic-site/src/Service/MonitoringTrackService.php::submitCourtSetSearch`,
`CourtSearchJobService::startCourtSet`) и держит предел 300 сайтов.

Как Legalic сейчас вызывает `createSearchJob()` для набора: на каждую цель —
`members`, `date_from`, `date_to`, `court_id` (у порталов — пусто, клиент его
отбрасывает), `process_types` (список), `unique_number: ''`; опции
`queue` (`adhoc` / `monitoring`), `max_pages`, `max_cases`.

## 2. Клиент: разбор адреса сайта суда — в пакет

Чтобы не спрашивать `/v1/resolve` про каждый из сотен сайтов набора, Legalic
перенёс правила `court-parsers/router.py` к себе:
`legalic-site/src/Service/CourtSet/CourtSiteResolver.php` (сверено с ответами
`/v1/resolve` 10.10.2026, тест `tests/Service/CourtSet/CourtSetRulesTest.php`).

**Предложение:** держать этот разбор в пакете (`CourtSiteResolver::resolve($url)`
→ `parser_id`, `court_id`, `court_id_can_empty`), а Legalic и vzysk-pro возьмут
его оттуда. Тогда при изменении `router.py` правится одно место. Или — пакетный
`/v1/resolve` на список адресов.

## 3. Справочник courts.lawmatic.ru

### 3.1. Ошибка данных: Люблинский районный суд Москвы

`77RS0015 Люблинский районный суд города Москвы` — сайт в справочнике
`https://lublinsky.msk.sudrf.ru`. Все остальные 34 районных суда Москвы — на
`mos-gorsud.ru/rs/<суд>`. Из-за этого Люблинский не покрывается порталом
«Суды общей юрисдикции Москвы» и опрашивается отдельно, через старый сайт.

- **Поправить** сайт на `https://mos-gorsud.ru/rs/lyublinskij` (адрес открывается,
  `/v1/resolve` отвечает `moscow / lyublinskij` — проверено 10.10.2026) и заодно
  пройтись по прочим судам Москвы, у которых сайт не на mos-gorsud.ru.

Проверка:

```bash
curl -sS -X POST "https://courts.lawmatic.ru/api/v1/courts/search" \
  -H "X-Auth-Token: ${COURTS_TOKEN}" -H "Content-Type: application/json" \
  -d '{"limit":50,"offset":0,"court_type":"RS","code":{"value":"77","match":"prefix"}}'
```

### 3.2. Регион суда — полем, а не префиксом кода

Legalic выбирает суды регионом по **первым двум цифрам кода** (`33…` —
Владимирская область). Это работает только для судов общей юрисдикции:
- у арбитражных код — номер **арбитражного** региона кириллицей (`А40` — Москва,
  `А41` — Московская область, `А56` — СПб), не код субъекта;
- апелляционные арбитражные — `08АП`;
- у военных цифры — округ, а не субъект (`25GV0004` стоит на Камчатке).

**Предложение:** в карточке суда — поле `region_code` (код субъекта ГАС, `33`) и
фильтр поиска `region` (один или список). Тогда в Legalic «все суды региона»
будут включать и арбитражный суд, и военные суды региона.

### 3.3. Фильтры, которых не хватает выборкам

- `court_type` — **списком** (районные + мировые одним запросом);
- `parent` — с глубиной: «все потомки» (сейчас — только прямые: у Мосгорсуда
  это районные суды, а участки мировых судей — уже внуки).

### 3.4. Весь справочник одним запросом

Legalic держит копию справочника на сутки (`legalic-site/src/Service/CourtSet/CourtCatalogCache.php`,
ночная команда `app:courts:catalog-warm`): 21 запрос по 500 судов. Это
укладывается в квоту, но удобнее:
- выгрузка всего справочника одним запросом (без полигонов, короткие поля:
  `id, code, name, court_type, website, parent_id`), или
- выгрузка изменённых с даты (`updated_since`) — тогда копию можно обновлять
  дельтой.

### 3.5. Подсудность по адресу

В старом `search.allcourts.ru` был фильтр `jurisdiction_address` (Delphi B2 искал
по «адресу должника»). В новом справочнике его нет. Сергей делает отдельный
сервис поиска суда по адресу — в Legalic под него уже заложена ручка
`/proxy/courts/by-address`. Если справочник будет участвовать (полигоны участков
мировых Москвы уже в нём есть), — согласовать, какой сервис за что отвечает.

### 3.6. Квота

Новая нагрузка от Legalic на справочник: ~21 запрос в сутки на копию плюс поиск
суда по названию и коду из интерфейса выбора судов (как и раньше). Если квоту
считают на токен — проверить, что её хватает.
